## Mixed note files

The independent slow-disk model demonstrated a concrete behavior with manually constructed authenticated files: an expired base plus an unexpired `.new` could be processed by AtomicFile, which discarded the pending file before the old base authorized whole-meeting expiry. A different base/backup pair similarly permits replacement before retention is adjudicated. Neither experiment proves that the pending version had been successfully committed, that a normal OS crash produces the layout, or that production user data was lost. Unknown history is nevertheless insufficient authority to destroy the possible sole valid version.

Reads now reject every unresolved `.new` before AtomicFile can discard it. They also reject a base and backup containing different encrypted bytes; identical duplicates retain the existing recovery path. Regular-file and bounded-size checks precede recovery. No unknown pending content is promoted or assigned a new deadline.

Maintenance can separately remove a family member whose exact meeting/length/ciphertext hash already has a confirmed durable expired-copy marker. It rechecks the target bytes, cancellation and unlock immediately before unlink; it preserves every different member and both shared aliases. The removal does not count as whole-meeting expiration. An isolated pending-only file still uses the prior authenticated expiry proof and retry path. After authorized companion cleanup, a remaining valid base can be processed normally. Recoverable file I/O failures remain errors but do not skip independently due meetings; authentication, clock uncertainty and cancellation still stop the scan.

Ordinary reads continue refusing a marked copy until maintenance has performed the permitted cleanup. The new helper does not silently restore a distinct backup, delete arbitrary paths, erase a whole meeting key for a copy, or swallow a generic SecurityException. Managed writers use the shared privacy lock; privileged replacement of files outside this process is not an atomic threat boundary these checks claim to solve.

## SQLite policy

AudioSegmentStore now expresses WAL and FULL synchronization in `SQLiteDatabase.OpenParams`, so connection configuration can be reapplied rather than relying only on a one-time PRAGMA. The six relevant write transactions apply and verify `secure_delete=ON` after acquiring their transaction-bound writer and before destructive SQL. The final segment-index deletion in whole-meeting purge is now also inside a checked transaction. Failure retains normal rollback and error propagation.

The earlier `rawQuery` cannot simply be described as having configured the wrong connection: AOSP prepares PRAGMA statements with primary affinity, and secure_delete can take effect during preparation. The verified gap is that a one-time native connection setting is not an explicit policy for future replacement connections. Do not claim that this app necessarily replaces its writer every 30 seconds. See [AOSP SQLiteProgram](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-15.0.0_r1/core/java/android/database/sqlite/SQLiteProgram.java), [connection configuration](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-15.0.0_r1/core/java/android/database/sqlite/SQLiteDatabaseConfiguration.java) and [transaction connection reuse](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-15.0.0_r1/core/java/android/database/sqlite/SQLiteSession.java).

This intentionally avoids registering the row-returning secure_delete PRAGMA through execPerConnectionSQL on all supported versions. The [Android 11 JNI implementation](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r1/core/jni/android_database_SQLiteConnection.cpp) rejects SQLITE_ROW through that non-query route; [Android 15](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-15.0.0_r1/core/jni/android_database_SQLiteConnection.cpp) has different PRAGMA handling. Transaction-bound rawQuery consumes and verifies the result without that compatibility assumption. API 35 compilation is not API 30/OEM runtime qualification.

No truncating checkpoint was added. WAL bytes, immutable backups, full old application snapshots, lost tombstones and physical remnants remain separate boundaries. A later checkpoint protocol must run after committed revocation, outside transactions/global privacy locks, verify the returned busy/log/checkpointed values, retain failures and allow later expiry transactions before retrying old cleanup. Never hand-delete an active WAL or add blocking truncation to each audio frame. See [SQLite checkpoint semantics](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint).
