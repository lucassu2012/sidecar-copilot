## Oboe: keep the timing-sensitive path independent

The pinned guide excludes disk/network operations, blocking synchronization, sleeping and stream stop/close from the audio data callback. It also distinguishes requesting a stream transition from observing its completion, and warns against closing a stream while another thread still reads or writes it. These principles support Sidecar's separation of cancellation admission, physical-input control and durable finalization. They do not make Java `AudioRecord.stop()` asynchronous or prove its latency. [Oboe guide at the selected release](https://github.com/google/oboe/blob/b115f47593969fd67a21e9f63640ffef749b5067/docs/FullGuide.md)

Oboe's FIFO uses fixed capacity and limits a read/write to the available space or data. That is useful evidence for a bounded handoff if Sidecar later separates sample acquisition from frame persistence. Sidecar must additionally retain its existing gap/error semantics, clear discarded plaintext and refuse post-cancellation samples. An unbounded executor queue is unsuitable for audio payloads; silently replacing missing source audio with generated silence would not establish recorded evidence. These are Sidecar-specific design conclusions, not claims that the FIFO implements its privacy policy. [FIFO implementation](https://github.com/google/oboe/blob/b115f47593969fd67a21e9f63640ffef749b5067/src/fifo/FifoBuffer.cpp)

The current API 30+ Java implementation does not need a new C++/JNI/NDK build to remove disk I/O from service controls. Oboe remains a future native-adapter candidate only if measured device behavior warrants it. Its routing, buffering and conversion behavior would need independent qualification before any replacement.

## WebRTC: useful cancellation checks, unsuitable shutdown behavior to copy

The reviewed `WebRtcAudioRecord` uses a volatile loop flag and checks it again after a blocking read before sending data to native code. Its lifecycle operations use a thread checker. Those are useful comparisons for Sidecar's stop latch and explicit source ownership. However, `stopRecording()` waits up to two seconds for the reader, then continues resource release even when the join times out. Sidecar should not copy that path as proof of safely completed input shutdown; its stop/ownership protocol must account for a worker that has not exited. The source also calls a samples callback from the capture loop, so a slow downstream callback is not automatically isolated. [Pinned recorder source](https://webrtc.googlesource.com/src/+/eeb7e6beb2e20c5a273922fdf22b75a75cc28ad5/sdk/android/src/java/org/webrtc/audio/WebRtcAudioRecord.java)

The class depends on WebRTC-specific native bindings, audio effects, logging/thread utilities and annotations. It is not a standalone drop-in Java recorder. Importing the full real-time communications stack would add unrelated integration surface to this persistence/control fix. No network or communications capability is proposed.

## Applying the findings within the frozen scope

The immediate implementation should keep cancellation admission independent of the lock that protects a blocked append, schedule device stop independently of persistence, and keep one clear owner for release. Stop requests during preparation must remain latched so delayed preparation cannot reopen input. Durable tail sealing, gap recovery and resource closure may finish later, but a timeout must not be reported as successfully saved or fully stopped hardware. These are proposed implementation properties to verify, not evidence that the current change already passes them.

Existing-scenario validation should stall preparation/append/fault recovery, issue pause/end/deletion, observe the synthetic source stop and main-loop responsiveness, then release the stall and verify final persistence and no stale restart. Such injected checks can establish ordering; they cannot establish OEM Binder, driver, microphone or flash latency. The real capture gate remains closed until applicable software and physical-device evidence is complete.

Screenpipe remains an architectural comparison under the prior exact-version license review. Its desktop capture model does not replace Sidecar's external capture and Android source adapters. None of the resources reviewed here changes that boundary or authorizes real recording, deployment or distribution.
