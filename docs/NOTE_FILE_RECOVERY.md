# Note file recovery and deletion checks

The latest implementation and candidate are documented in [DELETION_BOUNDARIES.md](DELETION_BOUNDARIES.md). That slice supersedes the unconditional pending-file retention described in this earlier 50216 record: only a fully verified expired exact copy may now be unlinked after a durable copy marker; shared keys remain. Unknown copies remain incomplete. The read-only helper description below is also historical; NoteFileSet now has a gated exact-pending deletion method. WAL limitations and the device regression requirements still apply.

This implementation slice keeps the frozen v1.5 requirements, product states and official test IDs. It changes local note-file admission and operation postconditions. It does not change the encrypted format, deadlines, key aliases, database schema or the real-capture gate. The prior `8B3E32FF` candidate and its device results remain historical evidence; they do not validate this changed source.

## Implemented behavior

- Inventory deduplicates `.enc` and `.enc.bak` for saved-meeting candidates. Maintenance additionally discovers `.enc.new`. A failed directory listing is an error, not an empty successful scan. Inspection itself never restores, reads or deletes a body.
- Reads retain the original unlock, whole-meeting deletion and trusted-clock checks before `AtomicFile.readFully`. Before decryption, the base must be a regular file and both companions must be absent. A failed backup rename or pending-file removal can no longer silently admit the previous base.
- Writes retain the existing encryption, plaintext cleanup and explicit file sync. After `finishWrite`, the base is read directly and compared with the exact new IV plus ciphertext, including length; both companions must be absent. Failed verification reports an error and attempts `failWrite`, preserving the original exception and any thrown cleanup exception. It does not claim a rollback succeeded.
- Whole-meeting deletion still commits its existing barrier before alias/file cleanup. Completion now requires all three paths to be absent, including directory or symbolic-link residues. Constructor retries and maintenance use the shared privacy lock. Cleanup failure leaves the barrier in force and reports failure.
- An isolated `.new` is neither promoted to a saved meeting nor silently discarded. The legacy writer might have reported success even if its final rename failed, so its suffix alone cannot establish whether the user was promised a save. Maintenance retains the file and reports I/O failure, while attempting other independent candidates; cancellation, authentication, clock and policy failures still stop the scan. This is an unresolved recovery item, not successful expiration cleanup. A pre-existing whole-meeting deletion barrier authorizes checked cleanup of all companions.
- A scoped static maintenance entry creates an internal store without the ordinary constructor's eager deletion replay, then runs the checked sweep; that temporary object never escapes. It processes all whole-meeting barriers before file inventory or clock-dependent reads, including IDs with no remaining file. First-time main-page worker initialization invokes maintenance before opening a normal store, so one old cleanup I/O failure cannot prevent attempts to revoke unrelated due notes. The original I/O failure is still reported after independent work and ordinary construction remains fail-closed. Confirmed mutations retain their existing authorization after leaving the page; ordinary reads cancel with the page ticket.

`NoteFileSet` provides package-private, read-only inventory/postcondition helpers. `NoteStore.ids()` now declares `IOException`; its application caller already executes in an exception-reporting background task. A package-private `AccessProbe.atomicFile(File)` factory supports deterministic failures in instrumentation; no UI or IPC override is exposed.

## Evidence and limits

The fixed [Android 15 AtomicFile implementation](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-15.0.0_r1/core/java/android/util/AtomicFile.java) logs some rename/unlink failures without throwing. App-level checks address these observable failures; they do not establish filesystem crash durability. Windows `File.renameTo` replacement behavior is not evidence of Android POSIX rename behavior.

The slow-disk workline's `task-2/atomic-sidecar-repro/HANDOFF.md` supplies a separate host comparison: old NoteStore `9FC62BEB` had three confirmed failures; intermediate `273F9575` plus NoteFileSet `46D79605` passed 291 checks across ten scenarios. Three assertions intentionally changed to the selected conservative behavior; this is not an identical unmodified red/green test set. Its AtomicFile port has an explicit Windows rename adaptation and uses simulated Android authentication/preferences/Keystore. That intermediate result does not cover the later scoped-maintenance entry in `84F46647` or Android platform behavior.

The final `84F46647`/`46D79605` source was separately retested in `android/build/atomic-host-current`: all 291 checks, ten scenarios and 32 JVM phases passed without changing that harness or its assertions. Its manifest preserves the intermediate-to-final source delta. These ten scenarios still do not directly execute the new static-maintenance entry or Android APIs.

The new five-package candidate is `50216D6B…`, frozen under `android/build/atomic-notes-20261110` with 66 inputs, complete APK hashes and build logs. Host tests passed 144 real temporary-file assertions for companion combinations, inventories, directory residues and exact commits. Android instrumentation targets actual `NoteStore`, scoped Android Keystore aliases and controlled `AtomicFile` failures; all 98 planned assertions are compiled but not run. No emulator or physical device is used in this work slice. The retention line has now reported its separate window released; a future serialized run must bind its own ownership and this candidate.

Known boundaries remain: an ordinary store cannot open through an unrecoverable existing deletion, although the scoped maintenance path continues independent I/O cases; unknown pending-only data has no new automatic recovery UI or retention decision; the checks do not prove flash, backup, WAL or power-loss erasure. They do not prevent malicious replacement of the entire app-data snapshot. Existing note deletion barriers still filter individually deleted attachments after an old authenticated backup is restored.

## WAL review and required platform work

No new normal-recovery bypass was demonstrated in the current audio store. Current database rows and managed read paths deny revoked material, but host SQLite marker persistence is not proof of Android wrapped-key extraction or recovered PCM. This slice does not alter WAL configuration, checkpoint timing, key wrapping or audio storage.

The next isolated Android experiment must record connection configuration and transaction boundaries, then compare normal close, abrupt process death and a held reader. Checkpoint results must include busy status and frame counts; a refused or incomplete checkpoint must not reverse committed revocation or block later independent key revocations. Verify database/reopen read denial and separately inspect permitted test-data copies. Evaluate `execPerConnectionSQL` only after checking the current and future pooled connections; a missing explicit call alone does not prove the current writer uses insecure settings. Never hand-delete an active WAL, block every audio frame on a truncating checkpoint, or equate checkpoint completion with physical erasure. See [SQLite WAL](https://www.sqlite.org/wal.html), [checkpoint semantics](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint) and [Android connection configuration](https://developer.android.com/reference/android/database/sqlite/SQLiteDatabase#execPerConnectionSQL(java.lang.String,%20java.lang.Object[])).
